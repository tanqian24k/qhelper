## 1. 产品概述

**一句话**：一个跨平台（网页先行）的个人减脂记录工具，用规则计算每日热量预算，帮用户把「吃进去的」和「体重的变化」记成可看的趋势。

- **目标用户**：本人及小范围亲友；个人自用定位，无账号、无支付。
- **开发方式**：用户无编程经验，全部代码由 AI 代写，用户按本规格的验收标准逐里程碑验收。
- **平台路线**：网页（PWA）先行 → iOS/Android（Capacitor 打包）→ 桌面端后置。
- **节奏**：1–3 个月内产出可日常使用的版本（见 §9 里程碑）。
- **界面语言**：简体中文；单位 kg / kcal（列表等显示处可加斤换算，存储与计算一律 kg/kcal）。
  - _口径澄清（2026-06）_：「**可加**」是可选显示增强，MVP 界面全部用 kg，斤换算未实现且不在 DoD 内。

### 1.1 明确不做（Out of scope，来自 map）

拍照识别食物、动态热量预算自动调整、账号体系、支付/商业化、云同步（MVP）。

## 2. MVP 功能规格

### 2.1 用户档案（onboarding）

首次启动引导填写一次：

| 字段 | 说明 | 必填 |
|---|---|---|
| 性别 | 男/女（BMR 公式分支用） | ✅ |
| 出生年份 | 推算年龄 | ✅ |
| 身高 | cm | ✅ |
| 活动系数档位 | 四档单选：久坐 1.2 / 轻度 1.375 / 中度 1.55 / 高 1.725 | ✅ |
| 当前体重 | 也可跳过——打卡后从测量流取最新值 | 可跳过 |
| 饮食偏好 | 忌口/素食等自由文本（为后续 AI 教练预留，MVP 不参与计算） | 选填 |

**验收标准**：四项必填未完成不能进入主界面；档案可随时在设置中修改；修改性别/年龄/身高/活动档位后，BMR/TDEE/预算立即重算。

### 2.2 目标设定（目标版本化）

- 目标 = **目标体重（kg）+ 每周减重速率（kg/周）**；预计达成日由两者自动推算（剩余体重 ÷ 速率 × 7 天），并随实际进度动态更新。
- **校验规则（保存时执行，来自 05 号票）**：
  - 🔴 拒绝：速率 > 1 kg/周 → 提示「更快减重会流失肌肉且易反弹，请降低速率」；
  - 🔴 拒绝：按速率算出的预算 < 安全下限（女 1200 / 男 1500 kcal）；
  - 🟡 警告可继续：预算 < BMR 但 ≥ 下限 → 显示黄条，用户须点「我已了解黄警风险」才能保存；
  - 🟢 通过：显示预算、达成日。
- **版本化**：保存新目标 = 封存当前版本（记录封存日）+ 生效新版本；历史版本列表可查；历史曲线可标注「当时的目标」（v1 至少做到版本列表，曲线标注可进 §8 路线图）。
- **维持模式**：体重达标或达成日过期后，引导进入维持模式——不设缺口、预算 = TDEE，继续记录与看趋势；再次减脂 = 建新目标版本。

**验收标准**：设定 −1.5kg/周被拒；女 30 岁 165cm 70kg 轻度设 −0.5kg/周（预算 ≈1403 < BMR 1420）出现黄警可继续；设 −1kg/周（预算 ≈853）被硬下限拒绝；修改目标后历史版本 +1。

### 2.3 热量预算（计算规格，来自 05 号票）

```
BMR  = Mifflin-St Jeor：男 10×kg + 6.25×cm − 5×年龄 + 5
                             女 10×kg + 6.25×cm − 5×年龄 − 161
TDEE = BMR × 活动系数（久坐 1.2 / 轻度 1.375 / 中度 1.55 / 高 1.725）
缺口 = 每周速率(kg) × 1100        （换算依据：1 kg 体脂 ≈ 7700 kcal）
预算 = TDEE − 缺口                （随目标版本固定，不随运动/停滞自动调整）
下限 = 女 1200 / 男 1500 kcal（硬）｜BMR（黄警线）
```

- MVP **不含运动加成**，无「今日额外消耗」入口。
- **平台期反馈（三色状态，只提示不改账）**：进度页每周对比「实际周均体重变化 vs 预期速率」——
  - 🟢 正常：未达偏快线（⊇ 预期的 ±0.25 kg/周带）；
  - 🟠 偏快：下降快于预期 **超 0.25 kg/周** → 提示关注（掉太快）；
  - 🔴 停滞：连续两周变化不足预期的 25% → 建议复核记录完整性与活动档位。
  - 🟢/🟠 共用同一 0.25 宽度、两档首尾相接，区间无空洞。
  - _口径修订（2026-06）_：原文为 🟢「±0.25 内」、🟠「超 0.5」，导致偏快侧 (0.25, 0.5] 无状态归属；现合并为同一宽度，阈值较原口径更早触发。
- 验收用例（沿用 05 号票）：女 30 岁 165cm 70kg 轻度 → BMR ≈1420，TDEE ≈1953；−0.5kg/周 → 预算 ≈1403（黄警）；−1kg/周 → ≈853（拒）。

### 2.4 饮食记录（本餐会话制，来自 04 + 06 号票）

- 结构：每日四**餐槽**（早/午/晚/加餐）→ 每餐槽下多条**食物条目**。
- **录入 = 本餐会话**（06 号票结论 1）：弹层内连续添加——搜食物 → 选餐槽 → 填份量 →「＋ 加入本餐」入暂存区（实时小计、单项可移除）→「完成本餐」一次入账；暂存区为空时关闭弹层不产生任何数据。
- **份量**：克数为存储真值；每条食物库记录带默认份型（如「1 碗 ≈ 250g」），提供 1 份/半份/2 份快捷按钮。
- **热量**：按每 100g 值 × 克数自动换算，允许手改（改热量则反推克数显示，克数仍是真值）。
- **快照复制**：条目记录时复制食物名与每 100g 营养值；此后修改/删除食物库不影响历史条目与报表。
- **补录**：任意过去日期可补/改/删，无限制。
- 今日页常显：预算 vs 已摄入 vs 剩余；超支显示红色「超出 N kcal」，不拦截记录。

**验收标准**：一餐连续加 3 种食物一次入账成功；改某食物库条目的热量后，昨日含该食物的条目数值不变；为上周某天补录一条成功且计入该日合计。

### 2.5 食物库（来自 02 号票）

- **内置精选库**：300~800 条常见中式食物，简体中文；JSON/SQLite 内置，体量 < 200 KB，完全离线。
- **数据来源（合规红线）**：
  - 主库：台湾卫福部食药署「食品营养成分资料库」（政府资料开放授权条款第 1 版——允许重制/改作/商用/再授权，仅需注明出处）；
  - 补缺校验：USDA FoodData Central SR Legacy（CC0）；
  - ⛔ **禁用**：《中国食物成分表》及其任何流传电子版（汇编作品，(2006)二中民终字第4147号判例确认内置侵权）；香港食安中心 NIIS（明示不得商业用途）。
- **最小字段集**：`id / name_zh / name_alias / category / source(tfda|usda|manual) / energy_kcal / protein_g / fat_g / carbohydrate_g / fiber_g / sugar_g / sodium_mg / editable`（均为每 100g 值）。
- **规模建议**：主食 ~60、蔬菜 ~100、水果 ~60、鱼肉蛋豆 ~90、豆奶 ~40、油脂调味 ~40、坚果零食 ~30、饮品 ~30、高频中式菜肴/外卖 ~80–150（`source=manual`，条目名标注「估算」）。
- **用户自定义食物**：与内置库同构存储；用户可新增（名称 + 每 100g 值或按份换算）。
- **署名**：App「关于」页注明两个数据来源及许可条款；每年核对一次台湾库新版。
- 搜索：拼音/关键字匹配名称与别名；常用条目置顶。

**验收标准**：离线（断网）状态下搜索、选食物、记一餐全流程可用；关于页可见署名；自定义食物可与内置条目同列表检索。

### 2.6 身体数据（统一测量表，来自 04 + 06 号票）

- 模型：某日某类型一个值的记录流（`date / type / value`）——体重 `weight`、体脂率 `bodyfat`、腰围 `waist`、臀围 `hip`…加新指标零改表。
- **多次打卡不拦截**：同日同类型允许多条（早晚各一次都保留）；曲线与进度评估用**日均值**，且日均值口径在图上可见（多次打卡的日期点带 `*` 标记，06 号票结论 3）。
- **入口常驻可见**（06 号票结论 2）：身体数据块已记 → 显示今日数值 + 「补记/修改」；未记 → 邀请态（「今日还没打卡」+ 主按钮 + 「不强制、可补录」说明）。
- 体脂率/围度选填；MVP 全手动输入，不接设备/健康平台。
- 趋势页：体重曲线（日均值）+ 三色状态块；曲线数据点可看当日原始记录。

**验收标准**：同日记录 70.0 与 69.3 两条，曲线出现一个带 `*` 的均值点 69.7，详情可见两条原始记录；删除误录的一条后均值即时更新。

### 2.7 数据导出与隐私（map Notes 要求的一节）

- **导出**：一键导出全部数据为 JSON（含档案、目标版本、条目、测量、自定义食物）；提供导入恢复。MVP 无云同步，导出是防丢失的生命线（换设备/清缓存）。
- **隐私基线**：
  - 所有数据仅存本机（浏览器 IndexedDB / 移动端 SQLite），不上传任何服务器；
  - 无账号、无追踪、无第三方统计 SDK；
  - 未来 LLM 教练上线时，仅用户主动发起的对话内容 + 明确列出的档案摘要会发送给所选 LLM API 供应商，且 key 由用户自持（见 §8）；本节承诺写入关于页隐私说明。
- **Web 存储持久化**：启动时调用 `navigator.storage.persist()` 申请持久存储（01 号票：iOS 系统可能回收未持久化的 IndexedDB）。

**验收标准**：导出 JSON 可在另一浏览器导入并完整还原；清空站点数据前导出、清空后导入，数据无损。

## 3. 技术选型（来自 01 号票）

| 层 | 选型 | 说明 |
|---|---|---|
| 框架 | **Vite + React（纯客户端 SPA）** | 网页先行体验最好；AI 语料密度最高；不上 Next.js（纯本地应用无 SSR 收益） |
| PWA | vite-plugin-pwa | 可安装到主屏、离线可用 |
| Web 存储 | **Dexie（IndexedDB 封装）** | 结构化存储 + 索引 + 版本迁移；localStorage 的 10 MiB 上限不够用 |
| 移动端 | **Capacitor**（后置） | 官方工作流：`npm run build → npx cap sync → npx cap run ios/android`；移动端数据层迁 **capacitor-sqlite**（iOS WebView 的 IndexedDB 可能被系统回收） |
| 备选 | Expo（RN + react-native-web + expo-sqlite） | 仅当确认「移动端才是主战场、Web 只是过渡」时切换 |

**架构铁律**：数据层必须先建**存储抽象层（Repo 接口）**——`FoodLogRepo / MeasurementRepo / GoalRepo / ProfileRepo / FoodLibraryRepo`——UI 只依赖接口，Dexie 与 SQLite 差异被隔离在实现层（04 + 01 号票合并结论）。

**已知风险与对策**（01 号票）：
1. iOS 存储回收 → 移动端迁原生 SQLite + `navigator.storage.persist()`；
2. 无同步丢数据 → §2.7 导出/导入为 MVP 必做项，数据模型带 UUID 与时间戳为未来同步预留；
3. App Store 上架需 Mac/云构建 + 开发者账号 → PWA 先行规避，上架在移动里程碑再议。

## 4. 数据模型（来自 04 号票，六实体）

```
Profile        用户档案（单例）：sex, birthYear, heightCm, activityKey, prefs, createdAt
GoalVersion    目标版本：id, targetWeightKg, weeklyRateKg, closedOn?, createdAt
               （有且仅有一个开放版本；closedOn 非空即封存）
FoodLibrary    食物库条目：id, nameZh, nameAlias[], category, source,
               per100g{ kcal, proteinG, fatG, carbG, fiberG, sugarG, sodiumMg },
               defaultPortion{ label, grams }, editable   （内置与自定义同构）
FoodEntry      食物条目：id, date, slot(breakfast|lunch|dinner|snack),
               snapshot{ nameZh, per100g… }, grams, kcal, createdAt, updatedAt
Measurement    身体测量：id, date, type(weight|bodyfat|waist|hip…), value, createdAt
               （同日同类型多条合法；日均值口径用于曲线）
Setting        杂项设置：key, value（如导出提醒、黄警确认记录）
```

关系：`FoodEntry.slot` ∈ 四餐槽；`FoodEntry.snapshot` 是录入时对 `FoodLibrary` 的值拷贝（非引用）；`Measurement(type=weight)` 的日均值是 BMR/预算/趋势的体重来源。所有记录带 UUID + 时间戳（为云同步预留）。

## 5. 交互设计基线（来自 06 号票：C「时间线·手账风」胜出）

- **信息架构**：一日一页时间线——今日预算块（剩余 kcal 大字）→ 身体数据块（常驻）→ 各餐块（按餐槽分组，含当日条目与小计）→ 本周趋势块（三色状态 + 曲线入口）；右下悬浮 ＋ = 记一餐。
- 五条交互结论（实现时必须遵守，详见 [06 号票 Answer](issues/06-prototype-core-flow.md)）：
  1. 本餐会话制录入（暂存区 + 完成本餐）；
  2. 记录入口常驻可见（已记→数值+修改；未记→邀请态）；
  3. 多次打卡不拦截，日均值口径图上可见（`*` 标记）；
  4. 目标编辑统一弹窗，红拦/黄警/绿过实时预览；
  5. 一日一页时间线架构。
- 参考资产：[prototype/core-flow-prototype.html](prototype/core-flow-prototype.html)（交互逻辑以此为准，代码按规格重写，不直接复用）。

## 6. 非功能需求

- **性能**：首屏 ≤ 2s（PWA 缓存后秒开）；千条级记录下列表与统计无感卡顿。
- **离线**：PWA 安装后核心流程（记录/查看/计算）100% 离线可用。
- **浏览器兼容**：Chrome/Edge/Safari 近两年主版本；移动端 iOS Safari ≥ 16、Android Chrome ≥ 110。
- **可维护性**：Repo 接口层 + 领域计算（BMR/预算/校验）纯函数化并配单元测试；UI 组件不写业务公式。
- **数据安全**：见 §2.7。

### v2.0 AI 教练对话（来自 03 号票）
- **模型**：智谱 GLM-5.3-Flash（≈¥1/月 @15 轮/天；免费 GLM-4.7-Flash 兜底）；OpenAI/Anthropic 作可选高级引擎。
- **接入**：客户端直连 OpenAI 兼容接口；**BYOK**——用户自填 key，Web 端存 IndexedDB（不导出至 JSON 的敏感字段单独加密），移动端存 Keychain/Keystore；**严禁把任何开发者 key 打进安装包**（OWASP MASWE-0005）。
- **交互**：教练可读档案摘要 + 近期记录（显式列出）；系统提示词含注册营养师角色、硬约束（不做医疗诊断、极端节食请求须拒绝并建议就医）；输出结构化（食谱带克数与热量）。参考开源：H1an1/health-coach、Nutrition-Buddy（使用前复核 license）。
- **二选一增强**（实现前再决策）：Cloudflare Worker 代理做「免配置」模式（参考 backmesh）。
- 交互与 prompt 设计仍是雾区，启动前补一次 grilling。

### 远期候选（雾区/范围外，未排期）
云同步与多设备（需先定义 Web↔手机互通形态）、拍照识别食物（GLM 视觉能力已具备，模型侧无需更换）、动态热量预算自动调整、桌面端（Tauri/Electron 复用 Web 代码）。

## 9. 里程碑（1–3 个月，AI 执行 / 用户验收节奏）

| # | 里程碑 | 内容（对应章节） | 验收方式 |
|---|---|---|---|
| M0 | 工程骨架 | Vite+React+PWA 脚手架、Repo 接口层 + Dexie 实现、CI 可跑 | 部署一个空壳页面可安装到主屏 |
| M1 | 记录闭环 | 档案 onboarding + 目标设定（三态校验）+ 预算计算 + 本餐会话制记一餐 + 食物库（首批 ≥300 条内置） | §7 前 5 项 |
| M2 | 身体数据与趋势 | 统一测量表 + 多次打卡/日均值 + 体重曲线 + 三色状态 + 任意补录 | §7 中间 3 项 |
| M3 | 安全与收尾 | JSON 导出/导入、关于页（署名+隐私）、persist()、验收清单全绿 | §7 全清 |
| M4（可选） | 移动端壳 | Capacitor 打包 Android/iOS + capacitor-sqlite 迁移 | 手机离线可用、数据迁入 |

M4 实际状态（2026-06）：Android 壳已交付并验证安装；数据层已实现双后端（Web Dexie / 原生 SQLite，按 `Capacitor.isNativePlatform()` 分流）。**iOS 未发布**：真机上的 IndexedDB 回收风险尚未验证，故 SQLite 分支缺真机验证——详见 [implementation-map.md](implementation-map.md) 待办。

每个里程碑 = 一个可独立验收的增量；里程碑内由 AI 小步提交，用户只看运行结果对验收标准。
